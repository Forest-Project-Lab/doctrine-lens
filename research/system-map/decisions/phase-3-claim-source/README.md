# 主張と出所を結ぶ(`supports`)。器の指紋を告知する規約を足す(作業の記録)

- 日付: 2026-08-17
- 位置づけ: **実験ブランチ内の作業の記録**であり、統治木の ADR ではない。
- 経緯: doctrine#294 第5信 G3 で当方が提案し、第13信 §3 で上流が
  「導出の全六面に不変。足してよい」と**実測つきで**応じた欄。あわせて第13信 §3 の
  「版が上がらなくても指紋を告知してほしい」という依頼を規約へ入れる。

## なぜ要るか

`provenance` は**記録単位**だった。一つの要素は `purpose`・`responsibilities`・
`not_responsible_for`・`owner` を持つのに、出所一覧はそれら全部をまとめて覆う。
**どの出所がどの主張を支えているかが書かれていない。**

上流の `map-draft-check/1` は v0.14.0 で出所ごとの機械の判定を返すようになったが、
それは**出所ごと**であって**主張ごと**ではない。結び目が無いと、画面に書けるのは
「この記録のどこかに検証済みの出所がある」までであり、第2信で当方が認めた「捏造」と
実質的に同じ粒度である。

## 器へ足した物

| 物 | 中身 |
|---|---|
| `$defs.Source.supports` | 任意欄。**同じ記録の欄名**の配列。例 `["guarantee","response_measure"]` |
| `$defs.Source.verdict` の説明 | 「**書き手の申告**である。機械が辿れたかはここに書かない」と明記(第6信 §4 の撤回の帰結) |
| `$comment` (4) | **版が上がらなくても byte が変われば tag と sha256 を #294 へ告知する** |
| `$comment` (1) の明確化 | 「いままで通っていた物」= その欄を使っていなかった文書、と定めた(下記) |

**版は上げない。** `required`・`enum`・制約のいずれも機械で突き合わせて不変であることを
確かめた(`$id` は `system-map/gold-model/0.2` 据え置き)。

| | 値 |
|---|---|
| 器の指紋(新) | `2be64371c3c648760e851fa48487a39d974a07f6aca897266c7fffb6f637be42` |
| 大きさ | 18446 byte |

## 途中で規約の穴を二つ見つけた

### 穴1: 制約を足しかけていた

最初 `supports` に `minItems: 1` と `items.minLength: 1` を付けた。差分検査に掛けると
**「制約の追加」として捉えられた** —— 旧器は `Source` に `additionalProperties: false` を
持たないので `supports: []` を通していた。新器は落とす。**受け入れる集合が狭まっている。**

0.1 → 0.2 のとき当方は同じ形(制約の追加)を分類し損ねた。今回は繰り返さなかったが、
**版を上げるのではなく、狭めない形に直した** —— 空配列・空文字列の禁止は M 層の仕事である。
器を最小に保てば (1) と (2) の境が曖昧にならない。

### 穴2: 規約 (1) が新しい任意欄について曖昧だった

厳密に読むと、**型の付いた任意欄を足すこと自体**が集合を狭める —— その鍵を偶然持っていた
文書は、旧器では無検査で通り、新器では型で落ちる。この読みでは型付きの任意欄は永久に足せない。

`$comment` (1) に一文足して、「いままで通っていた物」は**その欄を使っていなかった文書**を
指す、と定めた。**既存の欄への制約の追加は (2) のまま**である。

## 機械が検めること(M-P1)

`model:supports-names-real-fields`。**名乗った名がその記録に実在すること**は JSON Schema では
書けない(兄弟の欄名を参照できない)ので M 層が持つ。

1. 名乗った欄がその記録に実在する
2. `provenance` 自身を支えると名乗らない(自己言及)
3. **空配列を名乗らない**(書かないことと空を書くことは別である)
4. 空文字列の名を持たない

負例 3 件(`neg-supports-unknown-field` / `-self-reference` / `-empty`)で、破ると鳴ることを実測した。

## 実データ

対象1 に **9 件**結んだ。locator が支える先を明示している出所だけである。

| 出所 | 支える欄 |
|---|---|
| `maintainer` ← 「owner 欄・確定方針」 | `owner` |
| `doctrine` ← non-goals.md「第10・17項」 | `not_responsible_for` |
| `lens` ← 「要求文・何を解いていないか」 | `purpose` / `not_responsible_for` |
| `vscode` ← 「起点を選ぶ操作を求めない」 | `purpose` |
| `c-lens-honest` ← 「ADR-014…の五つが芯」 | `guarantee` |
| `c-doctrine-audit` ← 「検証節」 | `guarantee` / `response_measure` |
| `c-lens-performance` ← **沈黙の出所 2 件** | `verification_status` |
| `c-safety-na` ← 「第17項」 | `na_reason` |

**結ぶ作業の途中で、護りが二度止めた。** `doctrine.authoring` と `vscode` について
当方が `not_responsible_for` を名乗ろうとしたが、**その二つの記録にその欄は無かった**。
片方は実在する欄へ直し、もう片方は**結ばなかった**(locator が支える先が曖昧だったため)。
書かない自由は在る。嘘の名を名乗る自由は無い。

## 了解の記録が 18 → 21 に伸びた

他の三対象(`lens-shipping`・`celery`・`fixture-rare-states`)は `supports` を一件も
持たないので M-P1 が VACUOUS になる。**了解を置いた。**

理由の要点は三対象とも同じである —— **結んでいないことは「支える出所が無い」ではなく
「まだ書いていない」である。** 画面はこの三対象について主張ごとの出所を出せない。

`registry.json` の言うとおり、この一覧の長さが「機械が何も言えていない量」であり、
今回は正直に 3 件伸びた。

## この記録が保証していないこと

- **9 件の結びは当方の判断である。** locator が支える先を明示していると当方が読んだ、
  というだけであり、**その出所が本当にその主張を支えるかは機械が検めていない**
  (上流の門も引用の実在までしか見ない。#294 第6信 §2 の実測)。全て `review_status: proposed`。
- **97 件の出所のうち結んだのは 9 件である。** 残る 88 件は「支える欄を名乗っていない」
  状態であり、画面はそれらについて主張ごとの出所を出せない。
- 三対象は一件も結んでいない(了解の記録に書いた)。
- **上流の追随は当方の手の外に在る。** 告知するまで、上流は古い指紋の一枚を同梱し続ける。
- `supports` を**書き忘れた**欄と「支える出所が無い」欄を、画面が区別することは
  まだ実装していない。器と検査器の段階である。
