## 正すこと1 — 判定は「二層」ではなく三門である

`phase-1-record.md` は 37 行目でこう書いている。

> 判定は **build 時判定** と **ブラウザ実行判定** の二層に分かれる。

**これは自分の直後の箇条書きと食い違っている。** 同じ節の 41〜46 行は三つを挙げている ——
`validator(build 前・モデル検査)` / `build 時判定` / `ブラウザ実行判定`。数え落としたのは
一つ目、つまり `validate.mjs` である。

`INVARIANTS.md` の側も同じ落とし方をしていた。27〜29 行が挙げる仕掛けは二つで、
`gates.mjs` と全ブラウザ試験が表から落ちていた。

上流も独立に同じ食い違いへ到達している(doctrine#212 第2信)。

> 検収は「二門」と文書化されていますが、実際には **`prototype/gates.mjs` が三つ目の門**
> として機能しています。`acceptance-gates.md` だけを読んだ起草者は、両門緑のまま build で落ちます。

**判定は三門である。**

| 門 | 何を見るか |
|---|---|
| 模型の門(`validate.mjs`) | 模型単体で判定できるもの |
| build の門(`build.mjs` + `gates.mjs`) | 生成物と到達の計算 |
| ブラウザの門(`test-m13/m14/labels-browser.mjs`) | 実ブラウザの操作・通信・矩形 |

加えて、門そのものを見る段が三つある —— 正本の単一性(M-S1)・門の発火(M-N1)・
不変条件と検査器の対応(M-R1)。

これが再び食い違わないように、対応の正本を `registry.json` に置き、`test-registry.mjs` が
`INVARIANTS.md` の表と機械で突き合わせる。**表から仕掛けが落ちれば赤くなる。**

「二門」と書いてある `references/acceptance-gates.md` は上流の配布技能の中に在り、
こちらでは直せない。#212 へ訂正を提案する(実行原則 14)。

## 正すこと2 — 「PASS 14 / FAIL 0 / SKIP 2」の読み方

`phase-1-record.md` は M 層の通過状態をこう記した。

> **validator(build 前・モデル検査)**: M-01〜M-16、四対象すべて PASS 14 / FAIL 0 / SKIP 2。

数字は当時のとおりである。しかし**この 14 のうち、四対象合わせて 8 件は対象を一件も
見ずに出た合格だった**(2026-08-09 実測)。検査の形が「絞った集合を回し、違反が無ければ
合格」であり、集合が空でも合格になっていた。

| 対象 | 何も見ずに合格していた不変条件 |
|---|---|
| lens-shipping | M-04・M-15 |
| celery | M-04・M-06・M-15・M-16 |
| fixture-rare-states(架空) | M-04・M-11 |

M-14 も同じ形だった。四対象を束ねて数えていたため、到達可能な要素が 0 件の対象
(celery・fixture)が隠れていた。対象ごとに判ずると `Math.max(...[])` が `-Infinity` になる。

**SKIP 2 も合格ではない。** `validate.mjs` の末尾に在った M-13/M-14 の SKIP は模型を
一切見ない二行の文で、終了コードにも影響しなかった。同じファイルの冒頭は
「SKIP は合格ではない(発火しない門を緑と呼ばない)」と宣言していた。

いまは判定が五値になり、合格の桶に入るのは `PASS` だけである。空判定は `VACUOUS`、
判定不能は `SKIP` として現れ、出所つきの了解の記録が在るときにだけ個別に許す。
了解が期限を過ぎるか前提が消えたら、**了解の側が所見になる**。

現時点の了解は 16 件である。**この数が、この模型群について機械が何も言えていない量である。**

## 正すこと3 — M-07 は半分しか実装されていなかった

`INVARIANTS.md` の M-07 は二つの主張を一つの行に持っていた。

1. 全ての実体が `review_status` を持つ ← 実装されていた
2. `proposed` の値が正本表示(`confirmed` のみの投影)に混ざらない ← **どこにも実装が無かった**

`validate.mjs` は 1 だけを検め、2 については「正本表示への混入検査はプロトタイプ側
(Phase 1)」と印字していた。プロトタイプ側にその実装は無い(`grep review_status prototype/*.mjs`
は 0 件)。**誰も検めていないものを、誰かが検めていると印字していた。**

M-07a と M-07b に割り、M-07b にも検査器を置いた。ただし `confirmed` の実体が一つも無く、
`confirmed` だけを写した正本表示も存在しないので、検査器は `VACUOUS` を返す ——
**この不変条件はまだ一度も検められていない。** 登録され、発火し、「見る対象が無い」と言う。
それが正しい姿である。

## 正すこと4 — 偶発の通信失敗をリンクの破損として報告していた

`test-m14-browser.mjs` は到達の検査で、伝送そのものが成立しなかった場合(HTTP の返す
位置づけを一つも得られない)を、4xx/5xx と同じ「到達失敗」として扱っていた。

2026-08-09 の実測で、同じ木・同じ commit に対して**一度だけ全 9 要素が「接続不能」で
落ち、単体走行と再走行では通った**(生ログ `phase-2-baseline/m-layer/logs/RED-transient-network-as-fail.log`)。
curl では同時刻に HTTP 200 が返っていた。

判定を三値にした。

| 事象 | 判定 |
|---|---|
| 位置づけを得て 4xx/5xx | `FAIL`(リンクが壊れている) |
| 位置づけを得て 2xx/3xx、または 429 | 到達できた |
| 位置づけを一つも得られない | **判定不能**(`SKIP`。環境が答えられなかった) |

`SKIP` は合格ではないので、了解の記録が無ければ赤である。オフラインの走行は
「M-14 の到達を判定できなかった」と言い、緑とも赤(破損)とも言わない。

これを決定論的に再現する継ぎ目を置いた(`--force-offline` で到達しない代理を挟む)。
sleep や運に頼らずに判定不能の経路を起こせる。
