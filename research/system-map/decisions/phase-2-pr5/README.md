# PR5: 複数対象 overlay と配線(作業の記録)

- 日付: 2026-08-10
- 位置づけ: ADR-031(受理済)の実装。**これは実験ブランチ内の作業の記録**であり、統治木の ADR ではない。
- 主題: 一 build 一 overlay をやめ、**対象の並び順が意味を持たないようにする**。

## 何が壊れていたか

同じ形の欠陥が二つあった。どちらも **落ちない**ので、誰も気付けない。

1. **対象を位置で握っていた。** 画面へ渡す値が build の並びの添字だった。呼ぶ側は既に
   全て id を渡していたのに、返す値だけが位置だった。並べ替えれば静止画が別の対象を撮り、
   ラベルの掃引は別の対象を掃く。撮影の名前(`01-system-t1`)も同じ形の位置依存だった。
2. **overlay を生成側のファイル名で読んでいた。** 対象を増やしても読まれない overlay が
   黙って出る。壊れた入力・未知の形・未知の対象・重複も、名前に辿り着けないまま
   `ENOENT` で落ちるだけで、**何が悪かったのかを一つも言えていなかった**。

さらに測定で一つ見つかった:

3. **生成側が「候補 0 件」を `measured` と書いていた。** 総括は `.some()` の連鎖で決めており、
   記録が空配列だとどの `.some()` も偽になる。つまり **何も測っていない走行が最良の状態を
   名乗っていた**(実測: `overlay-lens-shipping.json` が状態 `measured` で記録 0 件)。

## 決めたこと

| 決めた | なぜ |
|---|---|
| `overlay` の役割を **全 4 対象**へ | 役割が空でないことは検めていたが、**完全であること**は誰も検めていなかった。手で選んだ部分集合は、データに埋まった人の判断であり再導出できない。あわせて「候補が在るなら役割を持つ」を機械で書いた |
| 候補の絞りは **緩めない** | `authority` は鮮度判定の権威(台帳 v3.2-10)。緩めると第二の権威を作ることになる。述語は `lib/overlay-candidates.mjs` が一本で持つ |
| 新しい状態 `no-candidates` | 記録 0 件と一対一で対応させ、**書込時と読込時の両方で**検める。片側だけでは、もう片側の欠陥に気付けない |
| `schema` の名は `0.1` のまま | 消費者は一つで、同じ PR の中で原子的に更新している。上げると target-1 の測り直しが要る。**所有者判断が要るなら止める** |
| `<option>` を生成時に埋める | 実行時に組み立てていたので、生成物の字面から対象の一覧が読めず、外から数えられなかった |
| 翻訳の口を消す(残さない) | 呼ぶ側は全て正本から採った id を渡すので、古くなりようがない。「知らない id を弾く」守りは、字面を書く場所が無くなった時点で不要になった |
| 撮影の名前から通し番号を捨てる | 番号は対象を挿すたび振り直しになる。同じ位置依存の別の姿である |

## この緑が保証していないこと

- **了解の記録 18 件については何も検めていない。** 2026-11-09 に一斉に期限切れになる。
- **三状態の文が「生成物に在ること」しか検めていない。** 実際に描かれることは、
  この段では確かめていない(字面の走査である)。描画の確認は PR6 のブラウザ段が受け持つ。
- **`--check` は鮮度の問いであって決定論の問いではない。** commit すると HEAD が進むので、
  commit 済みの overlay は構造上いつも一つ前の rev を指す。どの段にも入っていない。
- **上流の実体は版でしか照合できていない。** 固定 commit(`03fb4bf`)を clone して
  `git rev-parse HEAD` で照合したのは**この手順の中の shell** であり、`--require-pin` は
  版しか比べない(cache から引いた実体は `commit: null`)。commit まで保証する口は PR7 で作る。
- `overlay` の役割を広げたが、三対象の overlay は **記録 0 件**である。overlay の
  読み書きの経路のうち、実データを通るのは依然 doctrine-and-lens の 1 対象だけである。
- 合成の対象は target-1 の複製である。**まったく新しい形の模型**が通ることは検めていない。
