# 既定は語らない。語らない分を数で支える

## 背景

行は上流が返した status をそのまま出していた。実測で、**それが何も区別していなかった。**

```
1 行 :: 帰結の明細 / SPEC-006 / current / 2
2 行 :: コード側の面の受入 / TEST-005 / current
2 行 :: 拡張機能の部品の配置 / IMPL-001 / current
1 行 :: 帰結の明細の受入 / TEST-006 / current
```

70 節点を順に起点に置いて出た 273 行のうち、**非現行は 48 行（17.6%）**だった。
残る 225 行は、読み手が読み飛ばすべき語を一つずつ持っていた。

`ADR-014` が status を行に出した理由は「非現行が現行と交互に混ざる」ことであり、
**現行だと言うことではなかった。** `SPEC-006` の受入 14 も
「**非現行の行に** status が出て」と書いていた。実装だけが言い過ぎていた。

## 決定

### 1. 既定の値は語らない。既定から外れたものだけを語る

行に出す属性が、**大多数で同じ値を取るなら、その値は出さない。**
外れた値だけを出す。読み手の目は、語が在る行にだけ止まる。

「既定かどうか」を**この実装が判じてはならない。** 上流が持つ規則に訊く。
`_registry` は明示的にこう書いている。

```python
CURRENT_STATUSES = frozenset({"current", "accepted"})
# Other slices MUST use this, never a bare `== "current"`.
```

**上流が「素の比較を書くな」と書いている。** 従う。
そして `current` は `REQ-003` の門が走査する 28 語に入っているので、
**書こうとしても門が落とす。** 規律が二重に効いている。

### 2. 語らない分を、数で支える

`ADR-014` は「良い状態を空白で表さない。『壊れている 0 ・ 足りない 0 ・ 循環 0』と
数で言う」と決めている。**行から語を消すのは、この決定と正面からぶつかる。**

ぶつかりを、消す代わりに**数を足して**解く。要約の事実の行に非現行の件数を出す。

```
既に壊れている 0 ・ 足りない 0 ・ 範囲が無い 2 ・ 非現行 4
```

読み手は 4 を見て、明細の中に status の付いた行が 4 本在ることを確かめられる。
**空白が「良い」を意味するのではない。数がそう言い、行が裏を取る。**

これが `ADR-014` との線引きである。

| | 空白にしてよいか |
|---|---|
| 要約の数量 | **だめ。** 空白だと「測ったのか測っていないのか」が読めない |
| 行の属性で、要約に件数が出ているもの | **よい。** 数が「幾つ在るか」を言い、行が「どれか」を言う |
| 行の属性で、要約に何も出ていないもの | **だめ。** 空白の意味が画面から導けない |

### 3. 判じられない回は、隠さない

登録簿は部分失敗しうる（`SPEC-005`）。取れなければ**どれが既定かを判じられない。**

そのときは**全行に status を出し、非現行の件数を出さない。**
`ADR-017` 決定 1「画面は確かめたことだけを言う」。
**隠す根拠が取れていないのに隠すのは、確かめていないことを言うのと同じである。**

### 4. 危うい変換を、試験の届く層でやる

「取れなかった（`null`）」を「無い（空）」へ均す誤りは、この製品でいちばん多い欠陥である
（`ranges` で一度、`currentStatuses` でもう一度）。

**その変換を、単体試験が回せる層に置く。** 呼ぶ側は上流の値を素通しするだけにする。

実測で確かめた。最初はこの変換を `src/panel/lensPanel.ts` に書いていた。

```ts
currentStatuses: snapshot.registry ? new Set(snapshot.registry.currentStatuses) : null,
```

潰しの表に「空集合へ潰す」を足したら、**どの門も捕まえなかった**——
`src/panel/` は `tsconfig.test.json` の外に在る。

```
試験に守られていない直しが 1 件:
  - 取れなかった現行の集合を、空集合に潰す（全行が非現行に化ける）
```

模型（`src/model/consequence.ts`）へ移し、呼ぶ側は `registry: snapshot.registry` の
素通しだけにした。同じ潰しを**三つの試験が捕まえる**ようになった。

**層の切り方が、門の届く範囲を決めている。** 判断を門の外へ出さない。

### 5. 測った数には、刻印を添える

**この木は、統治文書を足すたびに育つ。** `CHANGE-010` の一周を書いている最中だけで
節点は 67 → 70 と動いた（`CHANGE-010`・`IMPACT-010`・`ADR-021`・`CHANGE-011` を足した）。

つまり**この変更を説明する数が、この変更自身によって古びた。**
独立の走査が、文書五つに散った 34 箇所の数が実測と合わないことを挙げた。

数だけを書かない。**いつの木で測ったかを添える。**

```
実測（497e13b の木・70 文書）で、全節点を順に起点に置いて出た 273 行のうち…
```

刻印が在れば、読み手は「いつの話か」を知り、古びたことも自分で分かる
（用語辞書の「刻印」——ビューが参照時点を記す——と同じ考えである）。

数は手で数えない。`tools/measure-tree.mjs` が刷る。
**手で数えた数は、次に誰かが直すときに二度と再現されない。**

### 6. 上流から取って使わない値を残さない

登録簿の問い合わせは `projectionTypes` を返していたが、`CHANGE-004` で地図を捨てて以来
**実装のどこからも使われていなかった。** 取得から落とす。

取って使わない値は、**次に読む人に「どこかで効いている」と読ませる。**
`currentStatuses` が実際そうだった——**必要な値が既に手元に在ったのに、
無いものとして設計を始めていた。**

## 却下した選択肢

### 却下 1 — status を副文へ落とす（判定を要らなくする）

行の見出しから status を外し、id と並べて副文へ置けば、判定は要らない。却下した。

**`ADR-014` の動機がそこで死ぬ。** 非現行の文書が「直すことになるもの」の一覧に
並んでいることは、**見出しの高さで気づける必要がある。**
副文へ落とすと、いちばん気づかせたい 17.6% がいちばん目立たなくなる。

### 却下 2 — 出す status を実装が選ぶ

`status !== "current"` と書けば一行で済む。却下した。

**上流が明文で禁じている**（`never a bare == "current"`）。
`accepted` が漏れ、ADR の行だけが全部「非現行」に見える。
そして `REQ-003` の門がこの一行を落とす。**書けないように既にしてある。**

### 却下 3 — 明細の中の分布から既定を決める

「この明細で最も多い status を既定とみなす」形なら上流に訊かずに済む。却下した。

**起点を変えるたびに既定が変わる。** 同じ文書が、ある画面では語を持ち、
別の画面では持たない。読み手は二つの画面を突き合わせられなくなる。
そして**それは俯瞰である**（`NONGOAL-001`）。この画面は分布に答えない。

## 帰結

- 行の 82.4% が語を一つ失う。280px での折り返しが減る。
- 非現行の 17.6% が、**画面で唯一 status を持つ行**になる。
- 要約に数が一つ増える。読み手は数と行を突き合わせられる。
- 登録簿から取る項が一つ減る。
- 「取れなかった」の扱いが、門の届く層に集まる。
- 文書の数に刻印が付き、古びたことが読み手に分かる。

## この決定が及ばないところ

- **要約の数量には及ばない。** `ADR-014` がそのまま効く。0 は 0 と書く。
- **記号には及ばない。** 記号は五つとも排他で、既定を持たない（`SPEC-006`）。
- **上流が既定を教えない属性には及ばない。** 訊く先が無ければ、全部出す。
  分布から決めない（却下 3）。
- **起点の欄には及ばない。** 起点は一件であって一覧ではないので、
  「並んだ中から外れたものを探す」という動機が無い。そして
  **いま自分が編集している文書が非現行かどうかは、それ自体が読みたい事実である。**
  起点の副文は `id · パス · 状態 · 更新日` のまま、状態を常に出す。
