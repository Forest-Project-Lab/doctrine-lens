# 実行体を選ぶ設定は作業フォルダから上書きさせない

## 背景

設定 `doctrineLens.pythonPath` と `doctrineLens.pluginPath` は、
どの実行体を起こすかを直に決める。scope を宣言していないので既定の `window` になり、
作業フォルダの `.vscode/settings.json` から上書きできる。

起動条件を満たす統治木の形（`doctrine_docs/_system/` を一つ置く）を備え、
`.vscode/settings.json` に細工した値を持つリポジトリを開いて信頼すると、
その中の実行体が走る。起動の直後に取得が走るので、地図を開く操作すら要らない。

## 却下した選択肢

**`machine-overridable` にする。** 利用者の設定で変えられ、遠隔の環境でも変えられる。
しかし作業フォルダ側の上書きが残る。監査の検証で、
`machine` なら作業フォルダの値が捨てられ、`machine-overridable` では残ることを実測した。
今回塞ぎたいのは作業フォルダ側の上書きそのものなので、これでは足りない。

**値を検めてから使う。** 実行体のパスが作業フォルダの外を指していれば拒む、など。
しかし「安全なパス」を機械で決めることはできない。
利用者が本当に自分の python を作業フォルダの中に置いていることもある。
判定を持てば、正しい使い方を塞ぎ、悪意ある使い方は抜け道を探すだけである。

**作業フォルダの信頼に委ねる。** 信頼していない作業フォルダでは拡張機能ごと止まる。
それは既定として効いている。しかし「作業フォルダを信頼する」は日常の操作であり、
信頼したことが「その中の実行体を走らせてよい」と同義であってはならない。

## 決定

`doctrineLens.pythonPath` と `doctrineLens.pluginPath` に `"scope": "machine"` を付ける。
この二つは利用者の設定と遠隔の設定でだけ持てればよい。

`doctrineLens.docsRoot` は作業フォルダごとに違うのが当たり前なので `window` のままとする。
ただし作業フォルダの外を指す値は受け付けない。読むだけとはいえ、
指せる先を作業フォルダの中に限るのは安いからである。

`capabilities.untrustedWorkspaces` を `supported: false` として明示する。
宣言しなくても同じ挙動になるが、Marketplace の頁に出るので、
利用者が入れる前に「信頼した作業フォルダでだけ動く」と分かる。

## 帰結

- 配布元不明のリポジトリを開いて信頼しても、そのリポジトリが実行体を差し替えられない。
- 作業フォルダごとに違う python を使いたい利用者は、遠隔の設定か利用者の設定で切り替える。
  作業フォルダごとの切り替えはできなくなる。これは受け入れる。
- `docsRoot` の値が作業フォルダの外を指したときは、統治木が無いものとして扱う。
  黙って外を読まない。
- 試験が manifest の scope を字面で守る。落とせば試験が落ちる。
