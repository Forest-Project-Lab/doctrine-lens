# 既定のキー割り当てを持たない

## 背景

`Ctrl+K Ctrl+D` と `Ctrl+K Ctrl+I` を二つの命令に割り当てていた。
公開前監査で、この二つが編集器の既定と衝突することが実測で確かめられた。

- `Ctrl+K Ctrl+D` は `editor.action.moveSelectionToNextFindMatch`（全言語）
- `Ctrl+K Ctrl+I` は `editor.action.showHover`（Markdown で当たる）

拡張機能の寄与は重み 400 台、編集器の中核は 100 で、解決は末尾から走るため拡張機能が勝つ。
さらに、キー割り当ては manifest の静的な寄与であり、**拡張機能が起動していなくても登録される**。
統治木を持たない利用者も鍵を失う。

## 却下した選択肢

**空いている和音へ移す。** `ctrl+k ctrl+g`・`v`・`y`・`z` が空いていることは確かめた。
しかしそれは「いま空いている」だけである。他の拡張機能も同じ隙間を狙う。
編集器の将来の版が埋めることもある。衝突の危険を先送りするだけで、無くしていない。

**文脈鍵で絞る。** 印が囲む範囲の中に居るときだけ効くようにすれば、被害は狭まる。
しかし狭まるだけで無くならない。範囲の中に居るあいだは、
やはり `Move Last Selection to Next Find Match` が使えない。
加えて、文字入力の位置が動くたびに文脈鍵を立て直す仕組みが要る。
被害を狭めるために仕組みを増やすのは釣り合わない。

**そのまま出す。** 利用者が自分で割り当てを直せる。
しかし「なぜ効かないのか」を突き止めるには、拡張機能が原因だと当たりを付けたうえで
キー割り当ての一覧を読む必要がある。原因に辿り着けない利用者のほうが多い。

## 決定

manifest に `contributes.keybindings` を持たない。命令だけを提供する。

割り当てたい利用者は自分で `keybindings.json` に書く。README に例を示す。

## 帰結

- 導入しただけで編集器の既定が変わることが無くなる。
- 命令への到達は、命令パレット・編集器の右クリック・見出し（CodeLens）・状態の帯に依る。
  いずれも既に在るので、失うのは「鍵を一つ覚えている利用者の一手」だけである。
- 将来どうしても既定の鍵が要ると判じたら、この ADR を置換する新しい ADR が要る。
  そのときは、空いている和音を選ぶだけでなく、
  「なぜ他の拡張機能と衝突しないと言えるか」を書くこと。
- 試験が manifest に `keybindings` が無いことを守る。書き戻せば試験が落ちる。
