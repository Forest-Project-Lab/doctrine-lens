# 書き込みを持つ画面は Lens ではない — 構想には製品を変えずに応える

## 背景

上流 issue 204 の System View 構想は、目的・責務・入出力・保証から実装へ降りる
目的別の画面を提案する。CHANGE-030 が履歴を、合意台帳 v3.1（同 issue、所有者確定）が
合意の全文を持つ。ここには**この統治木が持ち続ける判断**だけを書く。

構想は新しい意味モデル（構成要素・流れ・契約・保証状態）を持ち、その値は
「AI が推定した候補を、所有者が確認して昇格する」形で育つ。つまりどこかの道具が
**確認・昇格という書き込み**を持つ。

## 却下した選択肢

**既存の帰結画面に構想の表示を足す。** 一つの画面は一つの問いだけに答える
（REQ-002）。帰結画面の問いは「これを変えたら、何をどの順で直すか」であり、
構想の問いは別である。混ぜれば両方が濁る——一度そうなった（ADR-012）。

**いま NONGOAL-001 を書き換えて、図の禁止を緩める。** 非目標の各項は実測の理由を
持つ。理由が生きたまま適用範囲だけ狭めれば、非目標の文書が嘘をつく。書き換えて
よいのは、検証が門を通過し、**理由ごと**書き換えられるときだけである（台帳 v3-1）。

**検証のための第三リポジトリを作る。** issue・決定・CI・権限が三重になり、検証後も
第三の正本が残りうる。隔離は本リポジトリの実験ブランチで足りる（台帳 v3-2′）。

## 決定

1. **書き込みを持つ画面は Lens ではない。** この製品は統治木を書き換えず
   （NONGOAL-001）、その理由——描く道具が書きもすると、見えているものが自分の
   書いた結果かが分からなくなる——は、表示する正本一般に及ぶ。構想の意味モデルへの
   確認・昇格は、人の直接編集か、上流側の書く道具の受け持ちであり、
   この製品には入れない。表示するだけなら、別の画面として検証の先に検討できる。
2. **検証の間、この製品は変えない。** REQ-000・NONGOAL-001・画面・模型・橋は
   そのまま。検証は `experiment/system-map` ブランチの `research/system-map/` で
   行い、Phase 0–1 の完了前に `main` にも製品コードにも統合しない。
   実験ブランチの終端は必ず裁く——正式移管・検証継続・閉鎖のいずれかを
   Phase 1 終了時に判断し、両統治木へ記録する。人間試験が未実施の間の判定は
   `UNASSESSED` であり、正式移管を選べない（台帳 v3-3・v3-2′）。
3. **追跡索引の参照先を、宣言済みの契約に付け替える。** 上流が上流 ICD 002 に
   `trace-index-api` を宣言した（上流 PR 205）。SPEC-004 はこの宣言を名指す。
   呼び方も返る形も変わらない。

## 帰結

- SPEC-004 に宣言への参照が入る（文書のみ。CHANGE-030）。
- `.gitignore` に `Reference_material/` が入る（台帳 v3-11′）。
- 検証が進んでも、この統治木に新しい要求・仕様は**まだ**増えない。増えるのは
  Phase 1 の裁きが「正式移管」を選んだときであり、そのとき NONGOAL-001 の
  改定案（全面禁止から、画面ごとの禁止+理由へ）を証拠付きで出す。
- 実験ブランチは統治木の外に在る。**外に在るものは統治の外に在る**（CHANGE-025 が
  四度実測した形）。だからブランチの存在と終端条件を、この文書が名指して
  繋いでいる。ブランチが消えるか裁かれるとき、この帰結も更新する。
