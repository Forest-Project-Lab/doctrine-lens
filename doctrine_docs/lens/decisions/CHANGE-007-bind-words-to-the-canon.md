# 画面の語を、木が持つ正本へ結ぶ

## 変更内容

### 1. 画面が出した語の定義を、用語辞書から引いて脚注に出す

統治木の `GLOSSARY-001`（用語辞書の正本）は、画面が使う語をすでに定義している。

```console
$ grep -oP '^\| \K[^ |]+' doctrine_docs/_system/glossary.md
… 正本 投影 ビュー 刻印 現行 履歴 廃止 置換 アーカイブ 要求 依存 参照
孤児 逆孤児 ガード リンタ 用語チェッカー 起点 帰結 波 明細 記号 …
```

**lens はこれを一度も読んでいない**（実装からの参照 0 件。試験に一件在るだけ）。

初学者が「波って何？」「逆孤児って何？」と思ったとき、答えは**同じ木の中に在る**。
画面がそれを出していないだけである。

**正本を出すだけなので、二重定義にならない**（REQ-003）。
語彙をこちらが持つのではなく、木が持つ表を引く。

### 2. 用語辞書に無い語を、辞書へ足す

実測で、画面が出す次の 6 語が辞書に無い。

| 語 | 画面のどこに出るか |
|---|---|
| **指紋** | 所見の文に最も多く出る。「記録した実装の指紋と、いまのコードの指紋が食い違う」 |
| 循環 | 要約の一行と循環の欄 |
| 所見 | 脚注「この画面のどこにも出していない所見が N 件」 |
| 検査 | 脚注「上流の docs-audit（34 検査）を … に実行」 |
| 統治木 | 起点が無いときの文 |
| 範囲 | 要約の一行「コード N か所」、行のコード範囲 |

**「指紋」は画面に最も多く出る語なのに、辞書に一行も無い。**
辞書は「刻印」（ビューが記す参照時点）を定義しているが、指紋（範囲の内容の sha256）は別物である。

辞書自身が「承認語を増やす、または意味を変えるときは、ADR で決め、この表を更新する」と
要求しているので、`ADR-018` を立てて足す。

### 3. 生の項名を承認語へ寄せる

行の一文は `depends_on` という**上流の項名**をそのまま出している。

```
Has SPEC-005 in depends_on. Its premise changes.
depends_on に SPEC-005 を持つ。前提が変わる。
```

辞書は「依存」を承認語とし、`depends_on` をその括弧の中に置いている。
**日本語の側は承認語で書く。** 英語の原文は項名を括弧に落とす。

## 理由

`doctrine#153` へ「製品の目的を置く型が無い」を出したとき、実測でこう分かった。

> 木は 45 文書・ADR 14 本を持ち、監査は error 0 / warn 0 / advisory 0 である。
> **それでも「何を解こうとしているのか」が読めない。**

同じ構造がここにも在る。**木は語を定義しているのに、画面がそれを出していない。**
上流に頼む必要は無い——正本は既にこの木の中に在る。

役割別の読解でも、初学者・データサイエンティスト・営業の三役が
「この語が分からない」で止まっていた。**一つ直すと三役の問題がまとめて閉じる。**

## 要求元

`REQ-003`「統治の規則を二重定義しない」——語彙をこちらが持たず、木の表を引く。
`REQ-002`「一つの画面は一つの問いだけに答える」——**画面は増やさない。**
操作子も置かない。画面に出た語の定義を脚注に並べるだけである。

## 見えている難所

**どの語を出すかを、実装が語彙として持ってはならない。**
「画面に出た文字列と辞書の承認語を突き合わせ、現れたものだけを出す」形にする。
語の一覧を実装に書くと `REQ-003` の破れになる。

**辞書が取れなくても画面を止めない。** 取れなければ語の定義を出さないだけで、
明細そのものは今までどおり出す（`PartialFetch` と同じ扱い）。
