# どちらの向きに辿ったかを言う。捨てた事実を数える

## 変更内容

### 1. 「繋がらない」を三つに割る

いまの脚注は一行である。

```
43 documents are not reachable from the origin and are not listed
```

この 43 件は、**性質の違う二つを畳んでいる**。実測（起点 `SPEC-005`、木は 48 文書）。

| 区分 | 件数 | 実体 |
|---|---|---|
| 画面が出す（帰結） | 4 | `IMPL-001`・`SPEC-006`・`TEST-005`・`TEST-006` |
| **画面が出さない（起点が前提にしているもの）** | **10** | `REQ-001`〜`004`・`SPEC-001`・`SPEC-004`・`ICD-001`・`ADR-014`・`CHANGE-005`・`IMPACT-005` |
| どちらにも繋がらない | 33 | 残り |

`43 = 10 + 33` である。**前の 10 件は「影響が無い」のではなく「辿る向きが違う」。**
明細は `depends_on` を逆向き・`impacts` を順向きにしか歩かないので、
**起点が依っているものは一件も出ない**（SPEC-006 の設計どおりである）。

それを「繋がらない」と一語で畳むと、読み手は「無関係」と読む。
`REQ-001`（この製品が存在してよい理由）が出ないのは無関係だからではない。

脚注を二行にする。

```
起点が前提にしている 10 文書は出していない（この画面は逆向きに辿らない）
どちらにも繋がらない 33 文書は出していない
```

**三分割が全起点で破綻しないことを実測した。** 48 起点すべてで
`帰結 + 前提 + どちらにも無 + 起点自身 = 48` が成立し、
帰結と前提が重なる起点は 0 件だった（重なった場合の扱いは実装で決める）。

### 2. 起点自身の所見を捨てない

いまの実装は、起点に付いた所見を `findingsElsewhere`（「起点の外に所見 N 件」）へ落とす。
**起点自身の所見が「外」に数えられている。** 起点が壊れていても画面はそれを言わない。

起点の欄に記号と所見を出し、`findingsElsewhere` の定義を
「起点にも、明細のどの行にも属さない所見」に直す。

### 3. 所見の全項を運ぶ

上流の所見は `check` / `severity` / `doc_id` / `path` / `refs` / `message` の六項を持つ。
画面へ届くのは `message` だけである（`view.ts` の `row.findings.map((f) => f.message)`）。

- **`severity` を捨てている。** error と advisory が同じ見え方になる
- **`path` を捨てている。** 所見が指すファイルへ跳べない
- **`check` を捨てている。** 同じ文書に複数の所見が付くとき、区別が付かない

六項をそのまま運ぶ。**判断は足さない**——上流の値を素通しし、描き手が並べるだけである。

### 4. 要約の内訳が突き合う形にする

いまの要約は二行で、関係が画面から導けない。

```
4 documents to fix · 4 code ranges · 3 with nowhere to fix
broken 1 · missing 0 · cycles 0
```

`4` と `1 / 0 / 3` の関係が書かれていない。記号は排他なので
`documents = broken + missing + nowhere + fix + review` が常に成立する。
**和が一致する形で出す。** 循環は文書の内数ではないので別行に置く。

## 理由

四つとも同じ規律の破れである。`SPEC-006` の制約と `ADR-014` の決定に既に書いてある。

> **畳んだら必ず件数を書く。** 隠すことは抽象ではない。
> **数量の位置に、数を代弁する語を置かない。**

1 は**性質の違う二つを一つの数に畳んでいる**。2 は**起点自身を「外」に数えている**。
3 は**上流が届けた事実を捨てている**。4 は**内訳を出さずに合計だけ出している**。

`CHANGE-005` が直したのは「数の代わりに言葉を置かない」ことだった。
この変更が直すのは「**畳んだものを、畳んだと言う**」ことである。

### なぜ 1 が最も重い

他の三つは「読みにくい」だが、1 は**画面が事実でないことを言っている**。
「繋がらない」を読んだ人は「影響しない」と受け取る。
`REQ-001` が影響しないという主張は偽である——起点はそれを前提にしている。

この製品の主張は「推測せず、宣言された辺だけを読む」である。
その製品が、**宣言された辺を持つ 10 件を「繋がらない」と言っている。**

## 要求元

`REQ-002`「一つの画面は一つの問いだけに答える」。
**画面は増やさない。** 前提の側を出す画面は作らず、件数と理由だけを脚注で言う。

`ADR-014`「数の代わりに言葉を置かない。門は木の健康に依らない」の延長である。

## 独立の探索が見つけたもの（後から範囲へ足した）

この変更を起票したあと、**実装を書いた者とは別の走査**で画面の主張を実データと突き合わせた。
47 件の疑いが挙がり、反証段を通して 33 件が本物と判定された。欠陥単位に畳むと **12 個**である。

重さの内訳: `states-falsehood` 17 / `misleads` 11 / `omits-count` 5。

**すべて自分で再現してから範囲へ入れた。** 再現できなかったものは入れていない。

| # | 欠陥 | 再現した内容 |
|---|---|---|
| 1 | 起点自身の所見が消える | 起点に `error` を一件付けても `summary.broken = 0`、`findingsElsewhere = 0`。行にも要約にも脚注にも出ない。**起点が壊れていても「壊れている 0」と数で言い切る** |
| 2 | `findingsElsewhere` が「外」でない | `doc_id !== origin.id` で数えるだけなので、**画面の行に全文が出ている所見も「外に 1 件」に数える** |
| 3 | 強連結成分の取りこぼし | `A↔B, B↔C` のとき `cyclePath` が書き下す一巡は `A→B→A` で `C` が載らない。`C` は行にも循環にも出ず、**「届かない 1 件」に化ける**（起点から届くのに） |
| 4 | 件数が負になる | 存在しない id と相互に指し合う辺があると、`inCycle` に幽霊が入り `unreached = -1` になる |
| 5 | 記号の排他で事実が数から消える | `broken` かつ `missing` かつ範囲 0 の文書で `missing 0 · nowhere 0` と出る。**記号の排他は一行にどれを出すかの規律であって、数の規律ではない** |
| 6 | 要約の内訳が閉じない | 記号は五種なのに数として出るのは三種。`fix` と `review` はどこにも出ない。写しの `1+0+3=4` は偶然だった |
| 7 | 速い拍で判定が丸ごと消える | 保存のたび `findings=null / checksRun=0` に置き換わり、脚注が `ran 0 checks at <前回の時刻>` になる。**`ADR-008` が禁じた事故の再来**。`carryAudit` は `auditAt` と `staleIds` しか引き継がない |
| 8 | 波の見出しと行の一文が最長距離と食い違う | 「起点に直に載る」と言いながら、直の辺を持つ文書が後の波に居る（最長距離を採るため）。`through` が迂回路だけを名乗り、**存在する直の辺を名乗らない** |
| 9 | 循環に落ちた文書がどの数にも入らない | `summary` は `rows` だけを数える。循環の脚注が数えるのは**循環の本数**であって文書の数ではない |
| 10 | 循環が第 1 波を埋めると、無い波を名乗る | 「第 1 波が済むまで確定しない」と出るのに、画面に第 1 波が一行も無い |
| 11 | 範囲が取れないと全部 `?` に化ける | 取得の部分失敗で `ranges=null` になると `?? []` で空に潰れ、`rangeCount===0` から `nowhere` が付く。**取れなかったのか本当に無いのかが区別できない** |
| 12 | 題名の周り | 影に隠れた写しの題名を採る／空白だけの題名が主文になる／題名の脚注は `docMeta.size === 0` のときしか出ないので 48 件中 1 件欠けでも出ない |

**8 について。** 最長距離で並べる決定（`SPEC-006`）は正しい。誤っているのは**文のほう**である。
`IMPL-001` は `SPEC-005` を直に `depends_on` に持ち、かつ `SPEC-006` を経由してもいる。
`SPEC-006` の後に直すのは正しいが、「`SPEC-006` を経由して依存している」とだけ書くと、
**存在する直の辺を無いことにしている。** 両方を言う。

## 方法についての決定（ADR-015 へ）

**12 個のうち一つも、この製品の門は見つけていない。** 単体 174 件・突然変異 39 件・
写しの門・統合 10 件・監査すべてが緑のまま、画面は 17 箇所で事実でないことを言っていた。

見つけたのは**実装を書いた者とは別の走査**である。これは ECSS が
作る規格（E-40）と点検する規格（Q-80）を別冊に分け、
「追跡表は各節目で**別の者が**検証する」（`ECSS-Q-ST-80C §6.2.6.12`）と定めているのと同じ構造である。

`ADR-015` にこの一項を入れる。**自分の門が緑であることを、正しさの証拠にしない。**

正確な列挙は IMPACT-006 に置く。

**見積が外したのは二つ。**

一つ目は**欠陥の数**である。起票時に 4 件と見積もったが、独立の走査が 47 件の疑いを挙げ、
反証段を通した 33 件を欠陥単位に畳んで 12 件になった。三倍である。

二つ目は**上流の変更への追随**である。`SPEC-001` と `SPEC-004` を直したことで
`source_drift` が 5 件鳴った。一件ずつ確かめ、`SPEC-005` と `TEST-005` は
**追随を要さない**と判断してその理由を文書に残した（黙って日付だけ上げない）。
これは今回直した仕組みそのもの——**前提が動いたのに誰も辿り直さない**——を、
上流の機械が捕まえた例である。

### 門の側から出た欠陥

**突然変異の門が 47 行のうち 1 件を素通りさせた。** しかも最も重い欠陥である。

```
通った!! 判定の引き継ぎから所見を落とす（保存のたびに壊れている 0 へ落ちる）
```

実装は直っていたが、**それを守る試験が無かった。**
`cadence.test.ts` は `staleIds` と時刻しか見ておらず、`findings` と `checksRun` が
落ちても緑のままだった。受入を二つ足して 47/47 にした。

- `001-10h` 引き継ぐのは判定そのもの（速い拍で所見と検査が残る）
- `001-10i` **三つ組が別々に動かない**（時刻だけ進む・検査だけ落ちる、が起きない）

緑を報告する前に、素通りした潰しを実際に当てて**赤 3 件**を確かめてある。

**実装を直しただけでは、直したことが守られていない。** これは `ADR-015` が
言っていることの実例である。今回は自分の門が仕事をした。
