# 取得を二つの拍に分け、監査を保存のたびに走らせない

## 背景

いまは保存のたびに四つ全てを取り直している。この統治木（文書 29 本・走査 112 ファイル）
での実測は次のとおり。

| 取得 | 所要 | 規模に比例するか |
|---|---|---|
| 登録簿 | 28 ms | しない |
| `dep-graph` | 122 ms | 統治木の大きさに比例 |
| `trace-index` | 488 ms | **作業フォルダ全体**の大きさに比例 |
| `docs-audit` | 510 ms | **作業フォルダ全体**の大きさに比例（34 検査） |

後ろ三つを並行に走らせているので実効は約 630 ms である。
この規模では気にならないが、数千ファイルのリポジトリでは秒単位になる。
保存のたびに秒単位で待たされるなら、`autoRefresh` を切るしかなくなる。
切れば地図が古びる。どちらも避けたい。

## 却下した選択肢

**全部を保存のたびに走らせ続ける（現状）。** 実装が単純である。
しかし規模が上がった瞬間に使えなくなる。上がってから直すのでは、
その間の利用者が「重い拡張機能」として切る。

**取得の間隔を一律に延ばす。** 待ち時間の総量は減る。
しかし地図の追随も同じだけ鈍る。速い取得まで巻き添えにする理由が無い。

**監査を自前の判定で置き換えて速くする。** 指紋の突き合わせだけなら軽い。
しかし判定を持てば ADR-005 の決定を覆すことになる。速さのために統治を崩さない。

## 決定

取得を二つの拍に分ける。

| 拍 | 走らせるもの | いつ |
|---|---|---|
| 速い拍 | 登録簿・`dep-graph`・`trace-index` | 統治木かコードの保存のたび（畳んで 400 ms） |
| 遅い拍 | 上の三つ＋`docs-audit` | 起動時・明示の取り直し・速い拍の後の静けさ（既定 2500 ms） |

遅い拍の間隔は設定 `doctrineLens.auditDebounceMs` で変えられる。
`0` を与えると遅い拍は自動では走らず、明示の取り直しだけになる。

速い拍だけが走ったあいだ、指紋の食い違いの表示は前回の判定のままである。
古い判定を新しい事実に見せない。判定がいつのものかを画面に示す。

## 帰結

- 保存のたびの待ちが約 630 ms から約 490 ms へ下がる。
  規模が上がるほど差が開く（監査は検査が 34 あり、最も重い）。
- 指紋の食い違いの表示が最大 2500 ms 遅れる。これは許す。
  食い違いは「いま直せ」ではなく「後で取り直せ」の合図だからである。
- 大きなリポジトリでは `auditDebounceMs: 0` を選べる。
  そのとき食い違いは明示の取り直しでしか更新されない。
- 判定の時刻を画面に持つ必要が生じる。持たないと、
  古い判定を新しい事実と取り違える余地が残る。
