# Phase 2 を始める — 上流の判定を借りない

## 背景

所有者が Lens 側 Phase 2 の実装開始を裁定した。実験ブランチ内の可逆な開発の再開許可であり、
上流の是正完了を待つ必要はない、というものである。

**日付の食い違いを残す**: 裁定の文面は自身を 2026-08-10 と日付けているが、この記録を書いた環境の日付は
2026-08-09 である。どちらが正しいかはこちらでは決められないので、本文書の日付は実際に書いた日
(2026-08-09)とし、裁定の文面が名乗る日付を併記する。黙って片方へ寄せない。

再開してよい根拠は上流の側にもある。上流は #212 第3信(2026-08-09)で
上流から lens 側へ求めるものは無いと述べ、次の五件を lens の領分として置いた。

| 事項 | 出所 |
|---|---|
| M 層の定義(`artifact` を実現先に数えるかの不一致) | #212 第1信ギャップ7・第2信で独立に再現 |
| 検収の門の数(文書は二門、実体は三門) | #212 第2信・第3信 |
| `validate.mjs` の M-13/M-14 の無条件 SKIP | #212 第2信 |
| overlay が対象1に固定されている | #212 第1信ギャップ1〜6 |
| `doctrine-path.mjs` が古い複製を掴む | #212 第2信 |

同じ第2信で上流は、自分が第1信で書いた「捏造出所ゼロ」という label を**自ら撤回した**。
数値(所見 0 件・出所 55 件)は真だが、「所見 0 ⇒ 捏造出所ゼロ」は成り立たない —— 検証器へ故障を注入すると
約 35 の素通り経路が在り、全要素を捏造した模型が同じ返す値(所見 0)で終了コード 0 になることを実測している。

こちらにも同型の穴が在る。開始時点で実測した:

- `validate.mjs` は四対象すべてで `PASS 14 / FAIL 0 / SKIP 2`・終了コード 0 を返す。
  その中には `架空(実在の成果物は無い)` という証跡を持つ練習用の対象が含まれる。
- そのうち **8 件は、対象を一件も見ずに合格を出している**(celery の M-06・M-15・M-16 ほか)。
  検査の形が `filter した集合を回し、違反が無ければ合格` であり、集合が空でも合格になる。
- M-14 を対象ごとに判ずると、到達可能な要素が 0 件の対象が二つ在り、最大操作数が `-Infinity` になる。
  いまは四対象を束ねて数えているため隠れている。合わせて **10 件**。
- `validate.mjs` は M-13/M-14 を、模型を一切見ずに SKIP している。SKIP は終了コードに影響しない。
  同じファイルの冒頭が「SKIP は合格ではない」と宣言しているのと食い違う。

つまり、上流が撤回した種類の overclaim を、こちらは**まだ撤回していない**。

## 却下した選択肢

**(a) 上流の是正完了を待つ。** 却下する。上流は `map-draft-check.py` の素通り経路を台帳へ積み、強化は次の反復だと
明示した。待てば実験は触られないまま古びる。ADR-030 が「触れない検証は進まない」として退けたのと同じ形である。
こちらの五件は上流の作業と依存していない。

**(b) 正式移管まで一気に進める。** 却下する。H 層は `UNASSESSED`(独立の被験者が居ない)、#210 は所有者の判定待ちで
ある。移管は本裁定に含まれず、新しい決定が持つ。

**(c) M 層を緩めて上流の下書きを通す。** 却下する。上流の起草した模型が `artifact` を実現先に使い、build の門が
正しく拒んだ。ここで門を広げれば「要素からコードまたは証拠へ到達できる」という M-14 の主張そのものが空洞になる。
不一致は**緩い側を厳しい側へ揃えて**直す。

**(d) 空判定を今までどおり合格と数える。** 却下する。それは上流が撤回した推論をこちらで再生産することである。

## 決定

1. **実験ブランチ内の可逆な実装を再開する。** 範囲は overlay の生成と表示・任意の対象への一般化・M 層の検査・
   Doctrine 実体の解決・環境の頑健性・Lens 側の CI と回帰試験である。
2. **本裁定に含まれないもの**(触るときは停止して所有者の判断を仰ぐ):
   System Map の正式な製品採用と本番移管 / Marketplace 公開 / doctrine の正式スキーマへの昇格 /
   `proposed` から `confirmed` への昇格の自動化 / 書き込み機能を Lens へ持たせること /
   独立の利用者の実測なしに H 層を合格とすること / `main` の既定の挙動の変更。
3. **ADR-030 は置換しない。** System Map は実験の表示を保つ。H 層は `UNASSESSED` のままである。
4. **M 層の定義を裁く**(上流が委ねた一件): 実現先として数えるのは `code_range` と `test` だけとする。
   `artifact`・`document`・`external_doc` は根拠や参照であって、コードまたは試験への到達ではない。
   `gates.mjs` の側を維持し、`validate.mjs` と検証用スキーマを**それに合わせて厳しくする**。
   これで、第一の門が通ったのに build で落ちる形が消える。この裁きを #212 へ報告する。
5. **何も検めていない合格を合格と呼ばない。** 判定を五値(`PASS` / `FAIL` / `VACUOUS` / `SKIP` / `ERROR`)にし、
   合格の桶に入るのは `PASS` だけとする。`VACUOUS` と `SKIP` は、出所・確認日・記録者・再点検期限を持つ
   了解の記録が在るときにだけ個別に許す。了解の無いものは赤である。了解が古びたら了解の側が赤になる。
6. **Doctrine の実体を tag と SHA へ固定する。** 導入台帳や複製の並びから黙って選ばない。固定と食い違う実体を
   引いたときは、静かに測らずに申告する。固定が古びること自体を見張る仕掛けを別に持つ。
7. **E2E は2対象**(Doctrine と Doctrine Lens)で行う。Doctrine に依存しない第三の対象は**実施しない**。
   これは完了条件の未達であり、残件として記録する(所有者判断)。
8. **門の数を実体に合わせる。** 判定は三門(模型の門・build の門・ブラウザの門)である。不変条件と検査器の
   対応を機械が検める正本を置き、検査器を持たない不変条件も、不変条件を持たない検査器も作れなくする。
   「二門」と書いてあるのは上流の配布技能の中の文書であり、こちらでは直せない。#212 へ訂正を提案する。

## 帰結

- **こちらの門は一度赤くなる。** 空判定 10 件が `VACUOUS` として現れる。了解の記録で緑へ戻すが、その差分が
  「何を検めていないか」の正直な一覧になる。
- **上流の下書きは、こちらの第一の門で落ちるようになる。** 落ちる場所が build から前へ移るだけで、通る下書きの
  範囲は変わらない。上流へ報告する。
- **「所見 0」を「捏造出所ゼロ」と言い換えない。** E2E の結果には、使った `map-draft-check.py` が上流自身の言う
  「まだ弱いまま」の版であることを併記する。
- **受理済みの ADR は書き換えない。** Phase 1 の終了記録が判定を「二層」と呼んでいる点は、その記録を編集せず、
  後継の記録で正す。
- 実験の資材は `research/` に留め、統治木へ持ち込まない。本文書の `llm_context` は `task` であり、
  平時の文脈には載らない(#210 条件3)。
- 次に波及が生じるのは、正式な製品採用または本番移管を裁くときであり、それは新しい決定が持つ。
