# 数の代わりに言葉を置かない。門は木の健康に依らない

## 背景

`SPEC-006` は既にこう定めている。

> **畳んだら必ず件数を書く。** 隠すことは抽象ではない。
> **良い状態を空白で表さない。** 「壊れている 0 ・ 足りない 0 ・ 循環 0」と数で言う。

この規律を自分で三箇所破っていた。実測で見つかった順に書く。

### 破れ 1 — 脚注が「全検査」と言い切っていた

画面は `上流 docs-audit（全検査）を 2026-07-30 09:14 に実行` と出していた。
「全検査」は数ではなく主張である。上流が検査を増やしても減らしても文言が変わらない。

上流 `docs-audit.py --json` の報告は `checks_run` を持ち、実測で 34 件の配列を返す。
橋（`src/doctrine/audit.ts`）はそれを読まずに捨てていた。**数が手元に届いているのに、
数の代わりに言葉を置いていた。**

### 破れ 2 — 門が「一件在ること」で「絞っていないこと」を代弁していた

`src/test/consequence.test.ts` の「上流の 34 検査すべてが橋を渡る」は
`nonTrace.length > 0` を見ていた。追跡以外の所見が一件来れば通る。

- **34 という数を検めていない。** 上流が 34 のうち 33 を絞っても通る。
- **木の健康状態に依っている。** いまこの木の所見は 1 件（`guard_liveness_gap`・advisory）で、
  それが偶然「追跡以外」なので通っていた。**木が完全に緑になると、
  橋が正しいまま門が赤くなる。** 門が製品ではなく木を測っていた。

これは記憶の教訓「緑を報告する前に、緑を出した仕組みを疑う」に当たる型である。
六巡の監査でも同じ型が四度出た。

### 破れ 3 — 行が非現行という事実を空白で表していた

行は `[記号][題名][id][後ろに N]` で status を持たなかった。
起点の欄だけが status を出していた。

実測で誤読を生む。`DECIDED-001` を起点に置くと 17 行が出て、そのうち 4 件が非現行
（`SPEC-002` が波 3、`SPEC-003` が波 4、`TEST-002` が波 4、`TEST-003` が波 5）で、
**現行と交互に混ざる。** 撤回して退役した文書が「直すことになるもの」の一覧に並ぶ。
`superseded_by` は橋が既に取っていたが、実装のどこにも使われていなかった（消費者 0 件）。

## 決定

### 1. 数の代わりに言葉を置かない

画面に出す数量は、すべて**数えた数**とする。「全部」「すべて」「多数」のような
数を代弁する語を、数量の位置に置かない。

脚注は `上流 docs-audit（34 検査）を 2026-07-30 09:14 に実行` とする。
34 は上流の `checks_run` の長さであり、上流が増やせば増える。

**この決定は数量にだけ掛かる。** 記号の意味や理由の一文のような、
数量でないものを散文で書くことは禁じない。

### 2. 門は木の健康状態に依らない

製品の性質を検める門は、この統治木の所見が 0 件でも 100 件でも同じ判定を出すこと。
木の中身に依る門は、製品ではなく木を測っている。

「橋が所見を絞らない」ことは二つに割って検める。

- **上流が走らせた数と、橋が伝えた数の一致。** 上流の `AUDIT_CHECKS` を実行時に読み、
  `checks_run` と突き合わせる。上流が検査を増やせば自動的に追随する
  （こちらが 34 という数を実装に持たない。REQ-003）。
- **橋が絞らないこと。** 偽のプラグインに、追跡と追跡以外を混ぜた報告を返させ、
  すべてが呼び手まで届くことを見る。**木を一切読まない。**

### 3. 行は status と、在れば後継の id を出す

行の副文に status を出す。`superseded_by` が在れば後継の id を併記する。

**彩度のある色を使わない。** 非現行は異常ではなく、ただの状態である。
`ADR-012` が「`!` と `~` に色を当てない」と決めたのと同じ理由で、
色を当てると「非現行＝悪い」という嘘をつく。従の色（`descriptionForeground`）で出す。

## 却下した選択肢

### 却下 1 — 検査の数を実装に定数で持つ

`const UPSTREAM_CHECKS = 34;` と書けば門は簡単になる。却下した。
`REQ-003`「統治の規則を二重定義しない」の破れである。上流が 35 にしたとき、
門は 34 を守り続け、**上流に追随しない側が正しいことになってしまう。**

なお、検査名は `src/test/bridge.test.ts` の走査（型名 20 + status 語 8 = 28 語）の
対象外なので、書いても門は落ちない。**落ちないことを理由に書いてよいわけではない。**
門の網羅が REQ-003 の範囲より狭いことは、`bridge.test.ts` の限界であって許可ではない。

### 却下 2 — 非現行の行を明細から落とす

`SPEC-002` のような非現行を最初から出さなければ、混ざる問題は消える。却下した。

`SPEC-006` の制約「畳んだら必ず件数を書く。隠すことは抽象ではない」に反する。
そして落とすと、**非現行に依存している現行の文書**が波から消える。
波の距離は非現行を経由して定まっていることがあるので、落とすと順序が変わる。
出したうえで status を言うのが正しい。

あわせて、上流 `dep-graph.py` の `--current-only` に依る案も却下した。
実測で `--current-only` は `--dependents` の返り値にしか効かず、
`--json`（`--classify-edges` と併せて呼ぶ形）には効かない。
呼び手が読むのは後者なので、一件も落とせない。

### 却下 3 — status ごとの説明を画面に出す

`deprecated` と `superseded` の違いを画面で説明したい。却下した（いまは）。

上流に `STATUS_MEANING` が無いので、説明を書くと**上流の語彙を実装に写す**ことになり、
`REQ-003` の破れになる。加えて status 語そのものは
`src/test/bridge.test.ts` の 28 語走査の対象なので、**書けば門が落ちる**。

上流へ issue を出した（[doctrine#153](https://github.com/Forest-Project-Lab/doctrine/issues/153)
に併記）。上流が表を持てば、こちらは表を引くだけで出せる。それまで出さない。

## 帰結

- 画面に出る数量は、すべて上流の数か、こちらが数えた数になる。
- 上流が検査を増やすと、脚注の数と門の期待値が自動的に追随する。
- 門が木の健康に依らなくなるので、**木を緑にする作業と門を守る作業が独立する。**
- 行の形が変わるので、`DESIGN.md` §4 と `SPEC-006` §出力を先に直す（ADR-013 の規律）。
- **画面は増えない。** 問いは「これを変えたら、何を、どの順で直すことになるか」のままである
  （REQ-002・ADR-012）。

## この決定が及ばないところ

- **統治の側の欠落には及ばない。** コア／支援／汎用の分類、製品の目的を置く型、
  雛形の節の検査は、いずれも上流に概念か仕組みが無い。
  [doctrine#152](https://github.com/Forest-Project-Lab/doctrine/issues/152)・
  [#153](https://github.com/Forest-Project-Lab/doctrine/issues/153)・
  [#154](https://github.com/Forest-Project-Lab/doctrine/issues/154) として出した。
  **上流が動くまで、こちらでは何もしない**（暫定で書けば正本が二つになる）。
- **二枚目の画面には及ばない。** ADR-012 の予定表（二枚目=差分、三枚目=点検表）を
  追い越さない。
