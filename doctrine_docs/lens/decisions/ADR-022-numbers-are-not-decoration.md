# 番号は飾りではない。突き合わせを門にする

## 背景

`TEST-006` は冒頭でこう書いていた。

> SPEC-006 の受入基準の十二項に一対一で対応させる。

**一対一でなく、十二項でもなかった。** 実測で対応を出したところ、こうだった。

| `SPEC-006` の受入 | それを検めていた試験の名 |
|---|---|
| 15 起点自身に所見 | `006-16.` |
| 16 「外」の定義 | `006-17.` |
| 17 記号の和 | `006-19.` |
| 18 強連結成分 | `006-15.` |
| 19 辿る向き | `006-20.` |
| 20 範囲の不在と未取得 | `006-21.` |
| 21 語の定義 | 番号を持たない名前 |
| 22 出ていない所見の行き先 | `006-25.` |

そして仕様に番号の無い主題が四つ、番号を占めていた。

**誰も突き合わせていなかったので、ずれても誰も気づかなかった。**

気づいたのは `CHANGE-010` で受入 23〜26 を足したときである。
**既に別の主題が同じ番号を使っており、同名の試験が四組できた。**

実害が在った。潰しの判定は `not ok N - <名>` から**名前だけ**を取るので、
同名が二つ在ると「どちらが捕まえたのか」が報告から読めない。
`node:test` は同名を黙って許す。

## 決定

### 1. 受入 N を検める試験の名は `006-N.` で始まる

同じ受入を複数の角度から見るときは `006-Nb.` `006-Nc.` と枝番を付ける。
**枝番は角度の違いであって、別の受入ではない。**

### 2. 単体試験で見られない受入は、「画面側」と宣言する

編集器・実物の画面・CSS でしか見られない受入は在る（受入 1・10・11・12）。
それらは `TEST-006` の表で**受け持ちを名指す**。

```
| 10 | 画面側（npm run preview。<svg> の数を実物の画面で数える） |
```

**宣言も試験も無い受入を、門が落とす。**

### 3. 突き合わせを門にする

三方向を検める。三方向とも、故意に壊して赤くなることを確かめた。

| 検めること | 壊し方 |
|---|---|
| 試験も宣言も無い受入が無い | 受入を足して試験を書かない |
| 仕様に無い番号を名乗る試験が無い | 試験の番号を `006-99.` にする |
| 受入が「受入基準」の節に在り、番号が 1 から連番 | 受入を別の節へ移す／番号を飛ばす |

**書いた規則を、機械が毎回突き合わせる。** そうでない規則は、書いた翌日に破れる。

## 却下した選択肢

### 却下 1 — 番号をやめて、名前だけにする

対応がずれるなら番号を捨てればよい、と考えた。却下した。

**番号は「この受入を検めるものが在る」を機械が確かめるための鍵である。**
名前だけにすると、受入を足して試験を書き忘れても誰も気づかない。
ずれていたのは番号ではなく、突き合わせが無かったことである。

### 却下 2 — 仕様の受入を、試験の番号に合わせる

試験を直すより仕様を直すほうが差分が小さい。却下した。

**仕様が正本である。** 試験は仕様を検めるものであって、逆ではない。
仕様の番号を試験に合わせると、次に仕様を書く人が「試験に合わせて書く」ことになる。

### 却下 3 — 枝番も一意の受入として仕様へ書く

`006-2b` `006-2c` `006-2d` をすべて受入として書けば、対応は完全に一対一になる。却下した。

**受入は「何が満たされていれば良いか」であって、「どう確かめるか」ではない。**
角度の数だけ受入を増やすと、仕様が試験の写しになる（`REQ-003` と同じ形の二重定義）。

## 帰結

- 受入 27 件のうち 23 件が番号つきの試験を持ち、4 件が「画面側」と宣言される。
- 受入を足して試験を書き忘れると、門が落ちる。
- 試験の名が重複すると、門が落ちる（潰しの報告が読めなくなるため）。

## この決定が及ばないところ

- **番号が合っていることは、中身が合っていることを意味しない。**
  `006-15.` が受入 15 を本当に検めているかは、人が読むしかない。
  門が言えるのは「在る／無い」だけである。
- **他の仕様（`SPEC-001`〜`SPEC-008`）には、まだ及んでいない。**
  受入基準の節を持つ仕様すべてで節と連番は検めるが、
  番号つきの試験との突き合わせは `SPEC-006` だけである。広げるのは次の変更で測ってから。
