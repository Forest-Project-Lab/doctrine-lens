# 地図を捨て、起点からの帰結を一枚の明細で出す

## 背景

この製品は「統治木を一枚の地図として見る」ことを中心に据えて作られた。深度が四段、
レンズが四つのダイヤル。実装は動き、試験は 151 件が通り、監査も緑である。
それでも利用者はこう言った。

> 逆に疑問が増えるばかりだった。本質的に解決しないといけないことがわかってない気がする。

原因を実測で四つに分けた（CHANGE-004 §理由）。要点は一つに畳める。

**この道具は、事実を描いて、判断を出していなかった。**

「SPEC-003 と IMPL-001 が繋がっている」は事実である。読み手はそこで「で、それが何？」と
訊く。画面は答えを持たない。ところが**上流は答えを持っている**。`docs-audit.py` は
34 種の検査を毎回走らせ、`dep_cycle`（循環は異常）・`review_by_overrun`（期限切れ）・
`reverse_orphan_spec_no_test`（試験が無い）といった**判定**を返している。
実装はそのうち 11 種（`trace_*`）しか受け取らず、残りを `src/doctrine/audit.ts` の
四行で捨てていた。判定を捨てて位相を描けば、判断は読み手に押し付けられる。

さらに、地図そのものが幻を作っていた。33 辺のうち 18 辺は 9 対の相互ペアで、その中身は
「同じ一つの事実を両端から二回書いたもの」である。実装は `BIDIRECTIONAL_GAP` という
仕掛けで、その二本をわざわざ振り分けて必ず二本に見せていた。
**利用者の「依存しあっているのは異常？」は誤読ではなく、画面が立てた偽の文の正しい読解だった。**
本物の循環は 0 件で、その答えも `audit.ts` で捨てられていた。

判断の材料はすべて上流から届いていた。実装はその 6% しか使わずに、残りで絵を描いていた。

## 却下した選択肢

**地図を直す。** 列の順を依存の流れに合わせ、行を交差の少ない順に並べ、題名を出し、
辺を種類で塗り分ける。実測すると、行順を 6000 回最適化しても辺の交差は 31 から 24 までしか
減らない。原因が並べ替えではなく「二本の軸がどちらも意味を持たないこと」にあるためである。
そして最大の問題が残る——**直しても、画面は依然として事実しか言わない。**

**隣接行列にする。** 節点リンク図が破綻する規模なら行列が勝つ、という研究がある
（Ghoniem 2004）。しかし同じ研究は「小さなグラフでは節点リンク図が必ず勝つ」とも言う。
実測の密度は 0.022 で、被験実験が扱った最小の 0.2 の十分の一である。
**この木は行列が勝つ条件に無い。** 表現を替えても、答えるのが位相であることは変わらない。

**判定を地図に重ねる。** 異常な節点を赤く塗り、循環を太い線で囲む。判定は出るが、
「どの順で直すか」は依然として読み手が組み立てることになる。そして座標の問題が残る。

**ダイヤルを増やして問いを切り替える。** これが現状の設計であり、批判の対象である。
Hickey の基準では、柔軟にするために選択肢を足すのは easy であって simple ではない。
実測でも四つのダイヤルが全部効くのは L1 だけ（L0 = 1/5、L2 = 2/5、L3 = 0/5）で、
深度が配置と絞りの効きを決めている。独立していない。

## 決定

**入口の画面が答える問いを一つに絞る。**

> これを変えたら、何を、どの順で直すことになるか。

そのために次を定める。

1. **起点を利用者に選ばせない。** いま編集器で開いている位置（カーソル行）から、
   印が囲む範囲を引いて起点の文書とする。ファイルを開くことが問い合わせそのものになる。
   選ぶ座を減らすのではなく、**消す**。
2. **出力は上から下へ読む一本の明細とする。** 節点も辺も座標も持たない。
   `<svg>` を一要素も使わない。
3. **順序を出す。** 起点からの距離で波（第 1 波・第 2 波…）に分ける。
   順序の規則は「上流の `depends_on` ∪ `impacts` での最長距離」だけであり、
   `REQ→SPEC→IMPL→TEST` のような型の表を持たない（REQ-003）。
4. **判定を上流から受け取り、そのまま出す。** `audit.ts` の絞りを外し、34 検査すべてを
   受け取る。上流が書いた日本語の所見を一字も削らずに出す。
5. **記号を五つに固定する。** 重い順に排他で `× > + > ? > ! > ~`。
   各記号はちょうど一つの上流の事実から出る。

   | 記号 | 意味 | 出所 |
   |---|---|---|
   | `×` | 既に壊れている | `docs-audit` の severity=error/warn |
   | `+` | 足りない | `dep-graph --reverse-orphans` |
   | `?` | 直す場所が無い | 波及先だが結ばれたコード範囲が零件 |
   | `!` | 直す | `--dependents 起点 --transitive` に載る |
   | `~` | 見直す | `--impacts 起点` にだけ載る |

6. **`!` と `~` を別の記号・別の文にする。** 依存（前提が変わる）と影響（波及する）は
   上流が別の端として持ち「混ぜるな」と定めている。方向を矢頭で運ばず、記号と文で運ぶ。
7. **相互のペアを和で畳む。** `depends_on` ∪ `impacts` の集合として扱う。
   同じ事実を二回描かない。
8. **俯瞰に答えないことを画面に明記する。** 隠した件数を必ず書く
   （「起点に繋がらない 28 文書は出していない」）。隠すことは抽象ではない。

## 帰結

- **深度（L0〜L3）とレンズ（四つのダイヤル）が無くなる。** SPEC-002・SPEC-003 と、
  それらに対応する TEST-002・TEST-003、根拠となった ADR-002〜005 を降ろす。
- **REQ-001・REQ-002 を書き直す。** 特に REQ-002 は、出所（DDD §3.3.3）が
  「課題ごとに別のモデルを作ってよい」「世界地図に地下鉄の駅は不要」と言っているのに、
  「一枚を四つのダイヤルで切り替える」「画面は増やさない」という**正反対の結論**を
  書いていた。出所に合わせる。
- **問いが増えたら画面を増やす。** 一枚に抱え込まない。二枚目は「前回開いてからの差分」、
  三枚目は「木そのものの点検表」を予定する。それぞれが一つの問いに答える。
- **俯瞰を失う。** 初めてこのリポジトリに入る人は、この画面から木の形を得られない。
  受け入れる。俯瞰は NONGOAL に書く。
- **次数 0 の文書がこの画面に出ない。** 実測で ADR 11 件全部と `_system` の 6 件。
  「なぜこうなっているのか」への経路が落ちる。題名と本文への検索で回収する。
- **上流への依頼が一つ増える。** `dep-graph.py --json` が `title` を返さないので、
  当面は `_frontmatter` を別に呼ぶ。上流へ issue を立てた
  （Forest-Project-Lab/doctrine#149）。届いたら呼び出しを一本に戻す。
- **約 2,100 行が消え、約 1,465 行が無傷で残る。** 上流との橋は一行も捨てない。
- **`src/` に 14 箇所ある「実際に起きた」の注記のほぼ全部が、消える側に居る。**
  それらは品質の証拠ではなく、撚りが発行した領収書だった。
