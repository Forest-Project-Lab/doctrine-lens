# 画面は確かめたことだけを言う。自分の門が緑であることを証拠にしない

## 背景

`ADR-014` で「数の代わりに言葉を置かない」を決めた直後、
**実装を書いた者とは別の走査**で画面の主張を実データと突き合わせた。

47 件の疑いが挙がり、反証段を通して 33 件が本物と判定された。
欠陥単位に畳むと **12 個**。重さの内訳は `states-falsehood` 17 / `misleads` 11 / `omits-count` 5。

**そのあいだ、この製品の門はすべて緑だった。** 単体 174 件・突然変異 39 件・
写しの門（誤り 0）・統合 10 件・監査（error 0 / warn 0）。

見つかったものの一部を挙げる（すべて自分で再現してから直した）。

- `A↔B, B↔C` のとき `C` が画面のどこにも出ず、「起点から届かない 1 件」に化けていた。
  **`C` は起点から届く。**
- 存在しない id と相互に指し合う辺があると、件数が **`-1`** になった。
- 起点に `error` の所見が付いていても `壊れている 0` と数で言い切っていた。
  起点は行にならず、所見は行にも要約にも脚注にも出なかった。
- 「起点の外に所見 N 件」の「外」は `doc_id !== origin.id` でしかなく、
  **画面の行に全文が出ている所見も「外」に数えていた。**
- 記号は五種なのに数として出るのは三種で、`fix` と `review` はどこにも出なかった。
  写しの `1 + 0 + 3 = 4` は**偶然**である。
- 保存のたびに `findings` が丸ごと消え、脚注が `0 検査を走らせた時刻` になっていた。
  `ADR-008` が禁じた事故の再来である。
- 「起点に直に載る」と言いながら、直の辺を持つ文書が後の波に居た（最長距離のため）。
  行の一文は迂回路だけを名乗り、**存在する直の辺を無いことにしていた。**

## 決定

### 1. 画面は「確かめたこと」だけを言う。知らないことを断定しない

数量も、行の一文も、脚注も、**実際に計算した事実**だけを述べる。
計算していないこと・取れていないことを、断定の形で書かない。

具体の帰結:

- **取れていない値を「無い」と言わない。** コード範囲が取れなかった回に
  `直す場所が無い` と出してはならない。`ranges` は `null` を許し、
  取れていないときは記号を当てない。
- **一つの数に、性質の違う二つを畳まない。** 「繋がらない」は
  「起点が前提にしているので出さない」と「どちらにも繋がらない」に割る。
- **記号の排他は行の規律であって、数の規律ではない。**
  記号に負けた事実（`broken` に負けた「足りない」）も数える。
  `bySymbol`（和が文書数に一致）と `facts`（互いに排他でない）を分ける。
- **判定から導いたものだけを引き継がない。** 引き継ぐのは判定そのものである。
  `AuditCarry` は時刻・食い違いの id・**所見・走らせた検査**を一つの型で束ね、
  必ず同時に動かす。

### 2. 自分の門が緑であることを、正しさの証拠にしない

**門は「作った者が想像した壊れ方」しか見ない。**
想像しなかった壊れ方は、門を何本増やしても見つからない。

これは宇宙・航空の規格が既に制度にしている構造である。
`ECSS-E-ST-40C`（作る側）と `ECSS-Q-ST-80C`（点検する側）は別冊で、
後者の §6.2.6.12 は「追跡表は各節目で**検証されること**」を要求する。
作った者と点検する者を分ける。

したがって:

- **変更を閉じる前に、実装を書いた者とは別の走査を一度通す。**
  対象は「画面が出しているすべての文と数」であり、実装ではない。
- **その走査が挙げたものは、必ず自分で再現してから直す。**
  再現できなかったものは直さない（偽陽性を追いかけない）。
- **門が緑であることを、変更の記録に「正しい」の根拠として書かない。**
  書いてよいのは「門は緑だった」という事実だけである。

### 3. 上流の値は素通しし、判断を足さない

上流の所見は六項（`check` / `severity` / `doc_id` / `path` / `refs` / `message`）を持つ。
**六項すべてを運ぶ。** どれを重いと見るかは上流が決めており、
こちらが `message` だけに潰すと、`error` と `advisory` が同じ見え方になる。

## 却下した選択肢

### 却下 1 — 前提の側を出す二枚目の画面を立てる

「起点が前提にしている 11 文書」を出す画面を作れば、脚注で断らずに済む。却下した。

`REQ-002`「一つの画面は一つの問いだけに答える」に反する。
この画面の問いは「これを変えたら、何を、どの順で直すことになるか」であり、
「これは何に依っているか」は別の問いである。**件数と理由を脚注で言うに留める。**

`ADR-012` の予定表（二枚目=差分、三枚目=点検表）を、根の無い状態で追い越さない。

### 却下 2 — 循環に落ちた文書を明細の行として出す

循環の文書も「直すことになるもの」なので行に出したい。却下した。

**順が決まらないものに順を付けることになる。** この画面の主張は順である。
循環は別枠に出し、畳んだ件数（`summary.inCycle`）を数で言う。

### 却下 3 — 「外の所見」を出すのをやめる

「画面のどこにも出ていない所見が N 件」は、次に何をすればよいか分からない。
数だけ出すくらいなら消したい。却下した。

`SPEC-006`「畳んだら必ず件数を書く。隠すことは抽象ではない」に反する。
**ただし「数だけで行き先が無い」ことは残った課題である。** 次の変更で扱う。

### 却下 4 — 探索を毎回の変更で回す

別の走査を毎回通せば安全である。却下した（既定にはしない）。

費用が大きく、小さな直しに掛けると変更が止まる。
**変更を閉じる前に一度**通す。回す範囲は「画面が出す文と数」に限る。

## 帰結

- 画面が出す数量と文が、実際に計算した事実と一致する。
- 取れていないことと、無いことが、画面の上で区別できる。
- 判定は速い拍でも保たれる（`ADR-008` の意図が、新しい項にも及ぶ）。
- **`CHANGE-006` の記録には「門は緑だった」としか書かない。**
  正しさの根拠は、別の走査が通ったことと、挙がったものを再現したことである。

## この決定が及ばないところ

- **統治の側の欠落には及ばない。** コア／支援／汎用の分類、製品の目的を置く型、
  雛形の節の検査は上流に概念か仕組みが無い（`doctrine#152`・`#153`・`#154`）。
- **「外の所見」の行き先**には及ばない。件数は出すが、そこから何を開けばよいかは
  まだ画面が言えていない。次の変更で扱う。
- **意味的な正しさ**には及ばない。この画面が確かめているのは
  **宣言された辺の接続**であって、辺の内容が真かどうかではない。
  接続が完全でも内容が真とは限らない。
