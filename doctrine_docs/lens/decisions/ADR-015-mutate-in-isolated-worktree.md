# 潰しは利用者の作業木ではなく、捨てられる隔離木で当てる

## 背景

`tools/mutate-check.mjs` は、潰す対象を**利用者が編集している最中のソースそのもの**に
書いていた。戻し方の記録（`.mutate-restore.json`）も利用者のリポジトリの中に置いていた。

危険は既にこの道具自身が、実測としてコメントに書いていた。以下、シグナルの名は
POSIX の割り込み（SIGINT）・終了要求（SIGTERM）・捕まえられない強制終了（SIGKILL）を指す。

- 「try/finally はシグナルでは走らない……実測で、Ctrl-C の直後には潰れたソースと
  古い束の両方が残った。」
- 「**親の殻を止めても、この道具は止まらない。** 実測: 走らせた殻を止めたあと、この node の
  処理は生き続け、次の行を潰し、記録を書き直していた。止めた側は『止めた』と思って記録から
  戻し、その裏で新しい潰しが当たっていた。**木が二箇所潰れたまま『全件が緑』に見える状態が
  残る。**」
- 「走らせている間、木を触らないこと。同時に `npm run build:test` を叩くと、互いの束を
  作り直して両方の判定が汚れる。これも実測している。」

CHANGE-004 にも同じ事故が記録されている。

## 却下した選択肢

**戻し方の記録をもっと丁寧にする。** journal は**事故のあとの回復手段**であって、作業木への
破壊的な書き込み自体は防がない。SIGKILL・端末の切断・並行実行・通常の編集との競合では、
回復手段があっても利用者の木と検査結果の両方が汚れる。実測がそれを示している。

**注意書きで守る。**「走らせている間、木を触らないこと」は運用の規律であり、構造ではない。
規律で守る安全性は、忘れた一回で破れる。

**別の場所へ clone する。** 隔離は達せられるが、毎回ネットワークか全複製が要る。
同じリポジトリの `git worktree` なら、オブジェクトを共有して安く隔離できる。

## 決定

**潰しは、対象の commit から作った detached な一時 `git worktree` の中だけで当てる。
利用者の作業木へは一バイトも書かない。**

1. 対象の commit を解決し、リポジトリの外（一時ディレクトリ）へ detached の worktree を作る。
2. ソースの潰し・型検査・試験は、その隔離木の中だけで行う。
3. `node_modules` は作業木のものを繋いで使う（読むだけ。全複製も再取得もしない）。
4. リポジトリ単位の排他ロックを取る。二重の走行は潰しの前に早期に失敗させる。
5. 隔離木は捨てられるので、`.mutate-restore.json` を作らない。一行ごとの戻しは隔離木の
   中で行い、走行の終わりに木ごと消す。
6. 報告は隔離木を消す前に、外へ保存する。
7. SIGINT・SIGTERM・例外で後始末する。SIGKILL の後は、次回起動時に**孤児の隔離木だけ**を
   検出して片づける（利用者の worktree には触らない）。
8. 未コミットの変更を検査対象に含めたいときは、暗黙に作業木を使わない。明示の別 mode で
   snapshot を隔離側へ適用する。
9. 走行の前後で、作業木が汚れていないことを確かめる。汚れていたら**掃除せず**、その旨を
   報せるに留める（利用者の dirty state を自動で clean や reset しない）。

## 帰結

- 通常完了・試験失敗・SIGINT・SIGTERM・例外のどの経路でも、作業木は byte-for-byte 不変である。
- 潰している最中に作業木で build や編集をしても、隔離側の判定は汚れない。並行して働ける。
- 「木が二箇所潰れたまま全件が緑」は構造として起こりえない。潰す先が使い捨ての木だからである。
- 判定に「どの commit を潰したか」が刻まれる（ADR-014 の履歴の刻みと対になる）。
- 保証限界: SIGKILL の直後は隔離木がディスクに残る。次回起動が片づけるが、それまでは
  一時ディレクトリを占める。利用者の作業木が汚れることはない。
- 保証限界: 既定は commit を潰す。作業木の未コミットの変更は、明示しない限り検査対象に
  入らない。これは「暗黙に作業木を使わない」の裏返しであり、意図した取引である。
