# コード側の面の受入

## 受入基準への対応

SPEC-005 の受入基準の十項に対応させる。編集器を要する項と、要しない項に分ける。

| 確かめること | 手立て | 編集器 |
|---|---|---|
| 範囲の始まりに見出しが出る | 見出しを組む関数へ範囲を与え、行番号と内容を見る | 不要 |
| 見出しから文書を開ける | 見出しが持つ命令と引数を見る | 不要 |
| 食い違いが見出しと帯に出る | 食い違いの所見を与え、見出しの項と帯の種類を見る | 不要 |
| 印を含まないファイルに何も出ない | 範囲を持たないパスを与え、見出しが空であることを見る | 不要 |
| 範囲の外で命令を呼ぶと無い旨が出る | 範囲の外の行を与え、対応が見つからないことを見る | 不要 |
| 跳ぶ先が複数あるとき選ばせる | 二つの範囲を持つ文書を与え、選択肢の数を見る（統合試験は範囲が一つの文書で跳ぶ経路だけを踏む） | 不要 |
| 指紋の突き合わせが実装に無い | `src/` の字面を走査する | 不要 |
| 実装に日本語の表示文字列が無い | `src/` の字面を走査する（全角約物も含む） | 不要 |
| manifest の翻訳の鍵が英日で揃う | 二つの資源の鍵を突き合わせる | 不要 |
| 既定のキー割り当てを持たない | manifest に `keybindings` が無いことを見る | 不要 |

見出しを組む処理は編集器の型を使わない純粋な関数に切り出し、上表の十項すべてを編集器なしで確かめる。

編集器への登録そのもの（拡張機能が読み込めるか・命令が登録されるか・見出しが実際に出るか）は、
`@vscode/test-electron` で実際の拡張機能ホストを起こして確かめる。
入口は `npm run test:integration`、中身は `src/integration/suite/` にある。

### 親の VS Code の環境を持ち込まない

この試験を VS Code の中（統合端末・devcontainer・拡張機能ホスト）から走らせるときは、
親が立てた環境変数を落としてから起こす。落とすのは `ELECTRON_RUN_AS_NODE` と
`VSCODE_` で始まるものである。

落とさないと、新しく起こした Electron が「素の Node」として動き、VS Code の起動ではなく
拡張機能の入口を直に読み込む。出る誤りは `Cannot find module 'vscode'` で、
一見すると拡張機能側の欠陥に見える。実際は環境の取り違えである。
最小の hello-world 拡張機能でも同じ誤りが出ることが、切り分けの決め手になる。

この処理は `tools/run-vscode-test.mjs` が持つ。落とした変数名を毎回表に出すので、
効いていることが走らせるたびに見える。

## 退行観点

- 見出しを、範囲の無いファイルにも出さないこと。全ファイルに出すと、
  統治木を持たないプロジェクトで邪魔になる。
- 範囲の取得が済む前に空の見出しを出さないこと。出してから足すと、
  読み手には「この範囲には文書が無い」と読める。
- 行番号を数え直さないこと。上流が返す 1 始まりの値をそのまま使い、
  編集器へ渡すときにだけ 0 始まりへ直す。この変換を二箇所に書かない。

## 合否基準

上表の十項がすべて通ること。行番号の変換は、境界（範囲の最初の行と最後の行）で確かめる。

拡張機能ホストの試験も通ること。走らせるには GTK3 と X サーバが要る
（devcontainer の Dockerfile が入れている）。走らない環境では未実施として記録し、
通ったことにしない。
