# Doctrine Lens がやらないこと

やらないと決めたことを挙げる。理由まで書く。
「まだ作っていない」ものはここに書かない。ここに在るのは「作らないと決めた」ものである。

## 統治の規則を持たない

型・status・置き場所・依存の可否・指紋の突き合わせを、この拡張機能の中で判定しない。
上流 doctrine の判定の結果だけを読んで描く。

規則を二つ持てば、ゲートが通る状態と画面が示す状態が食い違う。
その食い違いは doctrine 自身が検出対象としている失敗の型であり、
それを描く道具が作り込んではならない。根拠は REQ-003・ADR-001・ADR-005。

## 図を描かない

節点と辺の図を描かない。作図ライブラリも持たない。`<svg>` を一要素も使わない。

一度は描いた。実測すると、二本の軸がどちらも意味を持たず（列は上流の登録簿の登録順、
行は id の辞書順）、辺の 52% が二列以上を飛び、無関係な箱を貫く辺が 24 本中 14 本になった。
そして描いても、画面は事実しか言わない。読み手は「で、それが何？」と訊く。
関係は文と記号で言える。循環でさえ `A → B → A` の一行で言える。根拠は ADR-012。

## 俯瞰に答えない

統治木の全体像・型の分布・ドメインの数を出さない。

答える問いを一つに絞ったことの代償である。初めてこのリポジトリに入る人は、
この画面から木の形を得られない。受け入れる。
一枚に俯瞰と帰結を畳めば両方が濁る（『ドメイン駆動設計をはじめよう』§3.3.3
「役に立つモデルはその目的にそった内容だけを表現します」）。根拠は REQ-002・ADR-012。

## 見え方を切り替える操作子を置かない

色の基準・絞りの条件・配置の方式・深度といったダイヤルを画面に持たない。

一度は持った。「柔軟に切り替えられる」ことを設計の中心に据えたが、
実測すると四つが全部効くのは一つの段だけで、深度が配置と絞りの効きを決めていた。
独立していなかった。柔軟にするために選択肢を足すのは easy であって simple ではない
（Hickey "Simple Made Easy"）。問いが増えたら画面を増やす。根拠は REQ-002・ADR-012。

## 印なしのコードを不足として鳴らさない

印（`doctrine:begin`／`doctrine:end`）が打たれていないコードを、
「根拠を持たないコード」として挙げない。

印は任意であり、印が無いことが欠陥かどうかは原理的に判じられない。
上流もこれを既知の限界としている（doctrine 側 ADR 054）。挙げれば擬陽性を量産する。
覆いの数字は示すが、不足としては鳴らさない。根拠は ADR-005。

## 統治木を書き換えない

呼ぶのは上流の読み取り専用の命令だけである。文書を直す・作る・消すことはしない。

それは doctrine の Skill（`doc-author`・`docs-curate` ほか）の受け持ちである。
描く道具が書き換えも行うと、「見えているものが自分の書いた結果か」が分からなくなる。

## 既定のキー割り当てを持たない

導入しただけで編集器の既定が変わることをしない。根拠は ADR-009。

## 複数の統治木を一度に混ぜない

一度に見る統治木は一つである。

別々の統治木は別々の登録簿とドメイン空間を持ち、同じ id が両方に在りうる。
混ぜれば衝突し、どちらの木の話かを読み手が判じられなくなる。根拠は ADR-006。
