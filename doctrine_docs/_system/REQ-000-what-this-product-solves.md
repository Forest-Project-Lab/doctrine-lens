# これを変えたら何をどの順で直すことになるかに、いま開いている場所から答える

## 要求文

この製品は、統治木を持つ人が編集器で作業している最中に、**ただ一つの問い**へ答える。

> **これを変えたら、何を、どの順で直すことになるか。**

答えは**いま開いている場所から**出る。利用者は何も選ばない。
答えは**上から下へ読む一本の明細**であり、どの行にも「なぜ居るか」の一文が付く。

### 何を解いているか

統治木は依存を持つ。だが**依存を持っていることと、変更の順が分かることは別である。**

- 依存は**辺**として書かれるが、辺を目で辿るのは人の仕事だった。
- 辿れたとしても、**どれを先に直すか**は辺の向きだけでは決まらない
  （`起点 → C → B` と `起点 → B` の両方が在るとき、`B` を先に直すと前提が二度変わる）。
- そして**壊れているもの・足りないもの・直す場所が無いもの**は、
  上流の監査が既に知っているのに、変更の順と同じ画面に並んでいなかった。

この製品は、その三つを**一つの明細**にする。順は**最長距離**で決まり、
各行の記号は**上流のちょうど一つの事実**から出る。

### 何を解いていないか

**俯瞰・構造・分類には答えない。** 地図を描かない。全体像を出さない。
答えないことを画面に書く（`NONGOAL-001`）。

**統治の規則を持たない。** 型・status・置き場所・指紋の突き合わせは、
すべて上流 doctrine が正本である。この製品は**判定の結果だけを受け取って描く**。

### 誰のためか

**統治木を持ち、編集器で作業している人。** 役割は問わない——
仕様を書く人、コードを書く人、試験を書く人、意思決定を追う人。

**辿るのに前提知識を要らなくする**のがこの製品の値打ちである。
「`SPEC` とは何か」を知らなくても、**題名と一文と順**が読める。

## 優先度

**必須。** この要求が満たされないなら、この製品が存在する理由が無い。

### 何が中核か

**中核はこれだけである。**

> 上流が返した事実から「これを変えたら、何を、どの順で、どう言うか」という
> **一つの答えを組み立てる判断**と、その答えを**「確かめたことしか言わない」へ縛る判断**。

上流の命令を一本呼べば返ってくるもの（事実・判定・語彙・統治の規則）は中核ではない。
その答えを**運ぶ橋・塗る筆・検める門**は、答えの形が変わったから追随するだけの支援である。

| 中核 | 何を持つ判断か |
|---|---|
| `REQ-000`（この文書） | 答える問いそのもの |
| `REQ-001` | いま触れているものから、直すことになるものを順に辿る |
| `REQ-002` | 一つの画面は一つの問いだけに答える |
| `NONGOAL-001` | 図を描かない・俯瞰に答えない・ダイヤルを置かない |
| `ADR-012` | 地図を捨て、一枚の明細にする |
| `SPEC-006`・`TEST-006` | 答えの形と、答えの定義 |
| `ADR-014` | 数を代弁する語を置かない |
| `ADR-017` | 画面は確かめたことだけを言う |
| `ADR-019` | 数を出したら行き先も出す |
| `ADR-021` | 既定は語らず、数で支える |
| `ADR-023` | 取れていない数を、その場に出さない |
| `src/model/consequence.ts` | 到達・循環の縮約・最長距離の波・記号の排他・仕分け |
| `src/model/view.ts` | **何を出さないか**の判断（上の五つの ADR を名指す箇所が 20 以上） |

**`ADR-014`・`017`・`019`・`021`・`023` の五つが芯である。**
どれも「言い過ぎない」ことを決めている。この製品の値打ちは、
順を出すことだけでなく、**確かめていないことを言わないこと**に在る。

### 何が中核でないか

**支援** — 上流への橋（`SPEC-001`・`SPEC-004`）、コード側の面（`SPEC-005`）、
画面の器と意匠、門と試験、辞書の読み取り、変更の記録（`CHANGE`／`IMPACT`）。
**必要だが、他所と同じやり方でよい。**

**汎用** — 統治の規則そのもの（上流 doctrine が正本）、編集器の platform、
束ね・型検査・CI の足場。**買うか借りる。**

**分類しない** — 退役した一式（`SPEC-002`・`SPEC-003` ほか）。
退役した文書は履歴であって、いまの投資の地図には載らない。

### 分類を項に持たない

上流は `subdomain`（`core`／`supporting`／`generic`）の語彙を持つが、
**この木ではその項を埋めていない。**

上流自身がこう決めている——**「投資の判断は決定（ADR）と非目標（NONGOAL）が
持ち続ける。項はそのどれの代わりでもない」**。中核はこの節が言い、
汎用は `NONGOAL-001` が言い、委ねたことは `ADR-001`・`ADR-018`・`ADR-020` が言う。

**項を埋めても画面は何も変わらない。** 自分の木で効かないものを足さない。
埋めるのは、機械が分類を使う先ができたときである。

---

`REQ-001` から `REQ-004` は、この要求を**どう満たすか**を機能の粒度で言う。

| | 何を言うか | この要求との関係 |
|---|---|---|
| `REQ-001` | いま触れているものから、直すことになるものを順に辿る | **この要求の中核をそのまま言う** |
| `REQ-002` | 一つの画面は一つの問いだけに答える | 「ただ一つの問い」を画面の規律にする |
| `REQ-003` | 統治の規則を二重定義しない | 「規則を持たない」を実装の規律にする |
| `REQ-004` | コードを読んでいるときに、その根拠の文書へ行ける | 「いま開いている場所から」をコード側から言う |

## 受入基準参照

この要求そのものに受入は無い。**満たされたかは、四本の `REQ` の受入で測る。**

- `TEST-006`（帰結の明細）——順・記号・要約・脚注
- `TEST-005`（コード側の面）——コードから文書へ
- `TEST-001`（橋渡し）——規則を持たないこと
- `TEST-004`（追跡索引の橋渡し）——文書からコードへ

**この要求は辺では指されない。** 横断の正本は本文で参照される（この体系の規約）。
ドメインの文書から `_system` の文書へ `depends_on` を張ると、越境依存のガードが拒む。
